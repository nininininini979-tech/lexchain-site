# LexChain 劳动争议初步法律分析意见助手

## 1. 定位

LexChain 面向陷入劳动争议的劳动者，提供基于用户自述事实和现行规则库的初步法律分析意见。系统帮助用户理解问题、整理证据、估算可能主张，并生成下一步行动和文书草稿。

产品不宣称提供正式律师法律意见，不替代律师、法律援助机构、劳动仲裁机构或劳动监察部门。只有经过人工复核的结果，才可以被导出为对外沟通材料；系统默认将结果标记为“初步分析”。

适用法域默认是中华人民共和国大陆地区劳动争议。页面必须显示法域和规则库版本，避免用户把结果误用于其他地区。

## 2. 目标与非目标

### 目标

1. 让普通劳动者在三分钟内完成一次可用的劳动争议初筛。
2. 优先覆盖拖欠工资，并逐步扩展到未签合同、违法解除、未缴社保、加班费、工伤等场景。
3. 将每个结论绑定到具体事实、证据状态和法条依据。
4. 输出可执行的行动路线，而不是只输出抽象的规则判定。
5. 保留现有确定性推理引擎和专业审计能力。

### 非目标

1. 不自动代表用户提交仲裁、投诉、诉讼或其他外部申请。
2. 不在没有事实和证据的情况下承诺胜诉、确定金额或确定时效结果。
3. 不让大语言模型直接决定法律结论；模型只能辅助整理文本，最终判定由规则、事实状态和人工复核共同约束。
4. 不在第一阶段覆盖全部劳动法或所有地区的地方性规则。

## 3. 用户模式

### 3.1 工人求助模式（默认）

首页使用通俗语言，以问题类型入口开始：

- 拖欠工资
- 未签劳动合同
- 被辞退或解除劳动合同
- 未缴社会保险
- 加班费
- 工伤或职业伤害
- 其他劳动争议

用户沿着四步流程完成案件初筛：

`事实收集 → 证据核对 → 初步意见 → 下一步行动`

界面只展示会改变当前结论的问题；未知事实允许保留为“尚未确认”，不能自动填充为否定或肯定。

### 3.2 专业审阅模式

专业模式保留现有规则库、O/F/P 道义逻辑、T/F/U 三值判定、例外推翻和符号证明。专业模式允许查看完整规则链、每个原子事实、例外条件和缺失事实，但不改变工人模式的结论。

专业模式的结论必须能够追溯到同一个案件事实对象，避免两套模式出现不同事实版本。

## 4. 意见报告结构

所有案件输出使用统一结构：

### 4.1 初步结论

使用四级结论：

- 已有事实足以支持
- 较大可能成立，但仍需关键证据
- 存在法律风险，事实不足以定性
- 当前无法判断

结论旁边显示“依据事实数量、待确认事实数量、关键证据数量”，不使用“必胜”“一定违法”等承诺性措辞。

### 4.2 适用法律

每项结论显示法律名称、条款编号、规则库版本和生效状态。规则库元数据必须包含法域、来源法律、更新时间和版本号。

### 4.3 事实依据

每个事实记录：

- 事实键和普通语言标签
- 值：是、否、未知或数字
- 来源：用户自述、上传材料、手动修正、规则推导
- 置信级别：已确认、待核实
- 影响的结论和规则

### 4.4 法律分析

分析按“构成要件 → 例外或抗辩 → 履行/违约 → 结论”展示。对每条适用规则，同时显示单位可能提出的反向解释和需要的反证材料。

### 4.5 可能主张与估算

金额必须显示计算公式和输入假设。结果分为确定输入、用户估算和待核实数据；缺少必要数据时输出区间或“无法估算”，不得伪造精确金额。

### 4.6 证据缺口

按优先级列出下一步最有价值的证据，并说明保存方法。例如工资流水、工资条、考勤、劳动合同、解除通知、社保缴费记录、催款聊天记录、证人信息。

### 4.7 行动路线

输出“现在、7 天内、需要专业帮助时”三段行动建议。路线只提供选项和风险说明，不替用户自动提交材料。

## 5. 拖欠工资 MVP

拖欠工资是第一优先级场景，首版必须支持：

### 5.1 事实采集

- 是否存在实际用工
- 入职和离职日期
- 每个月应发工资与实发工资
- 是否包含加班费、提成、奖金或其他报酬
- 是否仍在职
- 是否已向单位催收
- 单位是否承认欠款或承诺支付
- 工作地点和用人单位所在地

### 5.2 证据清单

证据按照“已有、部分有、没有、待确认”标记，并支持用户填写来源和备注。首批证据类型包括工资流水、工资条、考勤、劳动合同、聊天记录、催收记录、社保记录、解除材料和证人。

### 5.3 金额估算

首版只计算规则库已覆盖且输入足够的项目：拖欠工资本金、已确认的加班费、未签书面合同双倍工资差额、符合法定条件时的经济补偿或赔偿金。每项结果必须显示公式、输入月份和不确定性。

### 5.4 输出

报告必须优先告诉用户：

1. 哪些工资已经能够从现有数据确认欠付。
2. 哪些项目可能可以主张但还缺什么证据。
3. 应先向谁提出什么请求。
4. 哪些情况应尽快联系劳动监察、法律援助、工会或律师。

## 6. 数据与技术边界

保留现有 `engine.js` 和 `rules/labor-rules.json` 作为确定性判定核心，新增案件和意见层：

- `case`: 法域、地点、时间线、用户目标、状态
- `fact`: 键、值、来源、置信级别、更新时间
- `evidence`: 类型、描述、来源、状态、关联事实
- `claim`: 主张类型、计算输入、公式、金额或区间、法律依据
- `opinion`: 结论级别、依据事实、缺口、抗辩、行动路线、复核状态

规则引擎只负责评估事实和规则；意见编排器负责把结果变成普通语言；UI 负责展示和修正，不在模板中重新实现法律逻辑。

GitHub Pages 继续作为公开静态演示入口。静态模式不上传或读取 API Key，允许本地事实分析和浏览器端规则计算。涉及真实案件时，应优先提供本地保存和导出，后续再增加经过明确同意的后端存储。

## 7. 隐私与安全

1. 默认不要求真实姓名、身份证号、银行卡完整号码或住址。
2. 上传或粘贴内容前提示用户脱敏；界面提供遮盖敏感字段的说明。
3. 不自动把案件发送给第三方，不自动提交任何外部表单。
4. 任何云端事实抽取都必须显示发送目的、数据范围和静态模式替代方案。
5. 对工伤、暴力威胁、未成年人、群体性欠薪和报复风险设置人工转介提示。

## 8. 交互与视觉方向

- 默认移动端优先，适合低带宽和低阅读负担场景。
- 第一屏只呈现问题入口、进度和一个主要行动按钮。
- 使用清晰的状态颜色和文字，不依赖颜色单独表达法律结论。
- 结果页采用“结论摘要 + 证据缺口 + 下一步”顺序，专业推理折叠在后。
- 保留 LexChain 的深色、蓝色强调和符号审计风格，但降低理论内容在首页的视觉权重。
- 所有关键按钮和表单支持键盘、移动端触控和较大字号。

## 9. 交付阶段

### 阶段一：意见入口和拖欠工资流程

重构首页为工人求助模式，新增案件进度、工资月份录入、证据状态、初步意见摘要和行动路线；现有专业规则页面保留为专业审阅入口。

### 阶段二：意见编排和文书草稿

新增统一意见数据结构、法条引用、金额公式、证据目录、催款通知和仲裁申请书草稿。

### 阶段三：地区、版本和人工复核

加入法域/地区选择、法规版本管理、人工复核状态、导出前复核清单和法律援助渠道配置。

## 10. 验收标准

1. 新用户不阅读理论说明，也能在三分钟内完成拖欠工资初筛。
2. 每条结论都能查看其事实、证据状态和法条依据。
3. 缺失事实不会被默认成对用户不利的结论。
4. 金额估算能回显公式和假设，输入不完整时明确显示不能确定。
5. 专业审阅模式与工人模式使用同一案件事实和规则结果。
6. 页面不会自动发送或提交用户案件材料。
7. GitHub Pages 静态模式无 API Key，关键交互可离线完成。
8. 移动端首屏、表单和报告无横向溢出，核心流程有明确错误提示。
